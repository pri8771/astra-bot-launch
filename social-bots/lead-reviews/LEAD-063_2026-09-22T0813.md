### Finding 1 — unsafe reconciliation is detected but ignored

On stale takeover, existing `_reconcile(bot)` can return:
- `unauthorized_published > 0`
- `safe = false`

but `run_one_unit` currently records that result and proceeds unconditionally to `decision.run_cycle`, allowing a verified finish receipt after an unsafe reconciliation verdict.

### Source-grounded persistence detail

A stale-takeover-only gate would be insufficient.

`leasing.release()` deletes the owned lease. A subsequent acquisition of an empty slot creates a fresh lease with `reconcile_required=false`. Therefore, if the unsafe queue remains unchanged, gating only the stale-takeover invocation and then releasing would allow the next fresh unit to bypass the same unresolved violation.

There is no durable per-signal attempt ceiling, next-eligible time, exhausted/block state, or restart-stable retry policy.

These four immediate invocations prove a restart/retry opportunity, **not** four scheduler firings or elapsed-time reliability.

## Retry policy contract — SPECIFIED, IMPLEMENTATION HELD

No retry source change is released yet. This section supplies the explicit product policy required for a later repair.

Scope is narrowly **the same persona + signal repeatedly reaching `BLOCKED_REASONING_UNAVAILABLE` under an unchanged blocker condition**.

### Durable blocker identity

Retry state must be persona-private and keyed by:

`(bot, persona_id, signal_id, blocker_class, blocker_fingerprint)`

where:
- `blocker_class = reasoning_unavailable`;
- `blocker_fingerprint` is a deterministic digest of the normalized reasoning-route condition, including provider identity/mode, adaptive-required posture, dispatch/authorization availability class, and stable reason code — **not** free-form error text alone.

Restart, process id, lease generation and wall-clock time are not part of the identity.

### Attempt ceiling

- Maximum automatic attempts for one unchanged blocker fingerprint: **3 total attempts**.
- The first blocked attempt counts as attempt 1.
- No fourth automatic reasoning attempt for that same unchanged fingerprint.

### Backoff progression

After:
- attempt 1 -> next eligible after **15 minutes**;
- attempt 2 -> next eligible after **60 minutes**;
- attempt 3 -> mark **EXHAUSTED**, with no automatic time-based reattempt.

These are durable eligibility timestamps only. They do not authorize or install a scheduler.

### Block representation

Persist a persona-private durable retry record containing at minimum:
- bot/persona/signal id;
- blocker class + fingerprint;
- attempt count;
- first/last blocked timestamps;
- next eligible timestamp or null;
- state: `BACKOFF` or `EXHAUSTED`;
- last stable reason code/provider identity;
- reset/rearm audit fields.

A blocked/exhausted signal remains **unconsumed**. Exhaustion means "do not automatically retry this unchanged blocker", not "pretend the evidence was decided."

### Fairness

- Signals in BACKOFF or EXHAUSTED state are skipped for automatic selection while their block applies.
- The worker may select the **oldest other eligible unconsumed signal** for that persona.
- One invocation still handles at most one bounded signal/unit.
- A blocked oldest signal must not starve later eligible evidence.
- This policy must not mark skipped signals consumed.

### Automatic rearm/reset triggers

A blocked signal may rearm automatically only when the effective blocker condition materially changes, producing a different blocker fingerprint or no blocker at all. Examples:
- an adaptive provider becomes actually available;
- a valid scoped model authorization/manifest becomes active;
- the configured provider/mode changes;
- the prior unavailable/invalid route condition changes to a usable route.

When the blocker fingerprint changes:
- create/use a new retry identity with attempt count reset to 0;
- retain the old exhausted/backoff record as audit history.

**Time alone never resets EXHAUSTED. Process restart never resets it.**

### Signal changes

A genuinely new signal id is a new unit of evidence and has its own retry record. Do not mutate an existing signal merely to obtain a reset.

### Operator reset

Manual reset must be explicit and auditable:
- exact bot + persona + signal id;
- exact blocker record/fingerprint being reset;
- actor/lead reference;
- reason;
- timestamp.

Reset clears automatic exhaustion for that record but grants **no model/provider authority**. If the underlying blocker is unchanged, the next attempt will simply begin a new bounded retry sequence and fail closed again.

### Implementation hold

Do **not** implement this retry policy until ChatGPT issues a separate repair release after reviewing the reconciliation repair or another owner/lead request. This prevents two reliability changes from overlapping.
