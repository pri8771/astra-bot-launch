### Reproduced/root cause

The pre-repair metrics path treated any `int|float` as PRESENT. In Python, `bool` is an `int` subclass, and `float('nan')` / infinities are also floats. Giant integers can overflow on float conversion. Legacy stored PRESENT values were trusted during aggregation. Finite arithmetic could also overflow later in snapshot sums, ratios and snapshot differences.

### Repair reviewed

Exact candidate `30a2ebd...` introduces one shared finite-number admission helper and applies it at the relevant boundaries:

- fresh normalization: mapped bool/non-numeric/nonfinite/unrepresentable values become MISSING rather than PRESENT;
- raw payload remains preserved in `raw_metrics`; mapped raw name and expected metric kind remain available;
- legacy stored PRESENT values are defensively treated as missing during aggregation if invalid;
- aggregate reductions that overflow become `value=None` with `unavailable_reason=non_finite_result`, while coverage/count metadata remains truthful;
- ratio and snapshot-difference derived metrics fail closed to MISSING on invalid/nonfinite results;
- semantic behavior versions advance to reflect the corrected normalization/formula boundary.

The change is bounded to `runtime/metrics.py` plus focused tests. It does not redesign analytics storage, persona scoping or platform semantic mapping.

## Next reproduced defect — account route freshness

At current code, `runtime/account_routes.py::_route_ok` checks route type and `health_status` but never parses/requires/ages `last_verified_at`. Synthetic diagnostics reproduced:

- `health_status="verified"` + missing `last_verified_at` → `account_available=True`, `authorized=True`;
- the same route with `last_verified_at="2020-01-01T00:00:00+00:00"` → still available/authorized.

This contradicts `ACCOUNT_REGISTRY_SCHEMA.md`: `last_verified_at` is part of AccountRoute and stale verification cannot be presented as current connectivity.

### Lead-owned fixed freshness contract

For V0.8+ account-route availability, the following deterministic contract is now authoritative:

- **freshness horizon:** **24 hours** from `last_verified_at`;
- **future-clock allowance:** at most **5 minutes** ahead of evaluation time;
- `last_verified_at` is required for any route to be considered current/available;
- timestamp must parse as timezone-aware ISO-8601;
- missing, malformed or timezone-naive timestamp → unavailable/unauthorized;
- timestamp >5 minutes in the future → unavailable/unauthorized;
- timestamp age >24 hours → stale → unavailable/unauthorized;
- exactly 24 hours old is permitted; anything older is stale;
- health/route/capability checks remain necessary but never override freshness failure;
- freshness must be testable deterministically by injecting `now` into a pure/helper path; do not use filesystem mtime;
- no freshness result implies actual provider connectivity beyond the recorded verification event.

Rationale: route availability is an operational safety gate. A one-day horizon prevents stale sessions/account routes from being presented as current while remaining practical for daily verification; 5 minutes tolerates ordinary host clock skew without accepting materially future-dated attestations.
