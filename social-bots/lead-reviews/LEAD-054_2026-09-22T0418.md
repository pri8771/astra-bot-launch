## Independent source review

The prior `b5fd038` behavior persisted the due-rotation cursor only after `run_one_unit` returned. That created a real crash window: useful work and lease release could complete before the fairness cursor was durable, allowing the same bot to be selected again after a process/write failure.

The candidate moves claim persistence to an optional `on_claim` callback invoked by `run_one_unit`:

1. after the actual task lease is acquired;
2. under the lease generation fence via `Fence.fenced_commit(on_claim)`;
3. before stale-owner reconciliation and before `decision.run_cycle`.

The fence implementation checks lease id + generation while holding the same per-task lock used for takeover, invokes the callback while still holding that lock, then refreshes the lease. The rotation cursor itself uses the existing crash-safe JSON writer (temp file + fsync + `os.replace`).

Consequences verified by code path:

- if cursor persistence raises, the worker enters the existing failure path, writes failure evidence, releases its own lease, and **does not run the cycle**;
- if cursor persistence succeeds and useful work later fails, the successful claim remains durable and the next invocation rotates past that bot;
- a live-held candidate never invokes `on_claim`, so it does not advance the cursor;
- this remains a **claim rotation** ledger, not a completion-success ledger.

I found no source-level regression introduced by this bounded change.
