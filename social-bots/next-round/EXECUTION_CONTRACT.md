# Execution contract — next round

## Activation and scope

This is a next-round package, not an instruction to interrupt the running Fable artifact. ChatGPT remains lead. Workers cannot grant themselves acceptance, account scope, model budgets or public effects.

At the current worker checkpoint, preserve its branch and exact source/evidence commits. NR-01 reconciles those with canonical coordination before any new integration assignment. The existing SB-* artifact graph is retained; NR-* work closes missing integration and proof. If current work already meets a card, attach the evidence and skip duplicate implementation.

Priority: **working V2.3 first**, then V2.4–V3.0. Do not treat engineering-ready V2.3 as the owner's working-product target. Build ahead only when it does not delay that critical path and current ownership permits it.

## One integration lineage

Use a dedicated integration worktree based on the latest reviewed runtime lineage, plus the exact Fable feature commits and approved planning commits. Record them in BASELINE.json. Avoid merging entire historical branches just to obtain a few modules; inspect dependencies and preserve the stronger reviewed implementation. Do not force-push, rewrite another worker's branch, discard local work or merge main without the applicable authorization.

An integrator owns existing shared runtime files and H1–H4. Fable may build isolated modules; independent QA owns review harnesses/evidence. These are roles, not permission to spawn more sessions. Keep the current two-worker topology unless the lead explicitly changes it. Integration happens at small checkpoints, not after all 300 artifacts have accumulated separately.

## Read and act efficiently

Startup reads: root CLAUDE.md, current canonical state/assignment, NEXT_ROUND.md, and the active work card. Read deeper contracts only for the current boundary. Do not preload every packet. Use targeted diffs and symbol searches. Record a compact checkpoint with canonical SHA, source SHA, current task, claimed paths, evidence refs and next permitted action.

Use already-authorized lower-cost subagents only for bounded independent mechanical work. Keep architecture, safety review and final integration with the stronger worker. Do not create paid fallback or new model service accounts. The configured development chat and approved internal delegation are distinct from autonomous product/host model calls; the latter need the appropriate scoped grants.

## Small-task workflow

1. Select the smallest released task whose code prerequisites are present and reviewed to the required level.
2. Verify the active ownership claim. A stale branch name or start heartbeat is not proof of current exclusive ownership.
3. Define one observable outcome, allowed paths, an input/output contract and a test that would fail before the change.
4. Implement or reuse. Commit the bounded change with the SB-* or NR-* identifier.
5. Run focused/adversarial tests; run the relevant full suite on integration checkpoints and the full candidate before submission. Record discovered/pass/fail/error/skip counts separately.
6. Write evidence once, tied to the actual code/config/input hashes. Do not create successive commits merely to patch a self-referential source SHA; use source commit then evidence commit.
7. Submit, refresh canonical direction and continue another dependency-safe task. Do not self-accept, wait in a token-consuming loop, or skip an unaccepted gate that truly blocks the next action.

## Build and acceptance predicates

Use three distinct facts:
- build_ready: required interfaces and reviewed implementation inputs exist;
- engineering_verified: exact candidate passed the defined offline/integration tests;
- operational_accepted: lead accepted the required real evidence on a named environment.

The registry still has one canonical artifact status. Record narrower rehearsal evidence separately; never use ACCEPTED on a LIVE artifact merely because its offline rehearsal passed. A build predicate cannot grant an action. A parent bundle must cite its actual component and integration evidence, not just names. NR-01 must resolve apparent dependency cycles and stale status discrepancies before release.

## Checkpoints and stop rules

- C0: one baseline, consistent schema/registry, no unsafe route available.
- C1: trusted evidence -> reviewed draft -> prospective experiment on the actual runner.
- C2: target-host scheduling and real lead/worker direction cycle.
- C3: all H1–H4 wired; strategy -> goal -> task -> specialist -> verified result affects later work.
- C4: authorized real V2.3 scenario with compatible measurements and all prior required milestones accepted.
- C5: memory/segment/trend/cross-platform/allocation/self-audit feedback wired.
- C6: scoped multi-brand operation, restore, independent V3.0 decision.

Only advance operational version gates with their required evidence. Preserve the original V1.8/V1.9 and V2.4–V2.9 gates; do not skip them for numerical speed. For tests blocked on host, account, grant or data, write the exact next executable action and continue other released code work. If nothing is runnable, checkpoint and exit; continuation requires an actually installed scheduler or a later session, not a promise that the chat stays alive.

## Heartbeat and leases

Exactly one SESSION_ONCE start receipt per fresh session; no periodic in-session heartbeat watcher. Task locks/fences may still need renewal during work. Lease renewal is not another session heartbeat. After context compaction, use the existing session ID; after an actual new process/session, use a new one. Failed starts before canonical direction can be read leave a failure invocation receipt, not a fabricated successful heartbeat.

## Release standard

A release packet contains the exact candidate refs, declared supported deployment, commands/run IDs, raw-result hashes, independent review, original failures, budgets, capability/authority references, measured observation windows, recovery/restore evidence and remaining limitations. Main merge, public release, public posting and new spend are distinct gates. No milestone is promoted by this planning package.
