## Problem (LEAD-015 finding)

> "V03-004 fence protects main state/effects, but decision log/latest-decision
> writes remain outside the fence and filesystem multi-write effects are not
> transactional."

Concretely, the old `decision._commit` did:

```
fence.fenced_commit(do_commit)      # state + effects, under the task lock
append_jsonl(decisions.jsonl, ...)  # OUTSIDE the lock
write_json(last_decision.json, ...) # OUTSIDE the lock
```

`fenced_commit` acquires the per-task lock, verifies ownership, runs the commit,
refreshes the lease and **releases the lock** before returning. The two decision
records were then written with no ownership check. A worker that stalled after
`fenced_commit` returned but before those writes could resume after its lease had
expired and another worker had taken over, and overwrite `last_decision.json` /
append to `decisions.jsonl` with a stale, later-cycle-owned record — a durable
write after fence loss.

## Repair

- **Moved the decision-log and last-decision writes inside the fenced closure.**
  `decision._commit` now builds a single `do_commit()` that runs, in order:
  `effects()` → `rt.save()` → `ps.save()` → `append_jsonl(decisions.jsonl)` →
  `write_json(last_decision.json)`, and passes the whole thing to
  `fence.fenced_commit(...)`. Every worker-owned durable write of the cycle now
  happens under one ownership-checked lock acquisition. A fenced-out owner runs
  none of it (`FenceLost` is raised before `do_commit`).
- **Removed the false transactionality language.** Docstrings in `decision.py`
  (`run_cycle`, `_commit`, `_execute`) now state the guarantee precisely: it is
  an *ownership* gate, not a database transaction. Each individual file write is
  crash-atomic (temp+fsync+rename, per `jsonstore`), and an obsolete fence owner
  commits none of the writes; crash-time idempotent recovery across the
  multi-file set is explicitly named as deferred reliability work. No comment
  claims the multi-file set is "all-or-nothing" or "transactional".

The durable worker-owned writes now all gated by the fence:
bot runtime state, persona-private state (consumed ledger/hypotheses — see
SB-V03-005), experiment records, publish queue, content history, action history,
analytics events, decision history (`decisions.jsonl`) and last decision
(`last_decision.json`).

## Adversarial tests (`tests/test_fencing.py`)

1. `test_decision_log_and_last_decision_written_inside_fence` — a `ProbeFence`
   wraps the commit body and records, *inside the ownership-locked closure*,
   whether `decisions.jsonl` and `last_decision.json` exist yet. Both must exist
   before the fenced closure returns. **Against the pre-repair ordering this
   probe sees the files absent and the test fails**, so it is a true regression.
2. `test_stale_owner_cannot_write_decision_log_after_takeover` — full adversarial
   lifecycle: Worker A owns generation 1 and stalls at its commit boundary; the
   lease is forced stale; Worker B takes generation 2; A resumes and attempts to
   commit. A must write NO later cycle-owned durable record. The test inspects
   every surface — `decisions.jsonl`, `last_decision.json`, `bot_state.json`,
   `persona-social-b.json`, publish queue, `action_history.jsonl`,
   analytics `events.jsonl`, experiment files — and asserts none carries A's
   cycle; B is the sole owner afterward.
3. Existing `test_old_owner_cycle_commits_nothing_after_midcycle_takeover`
   extended to also assert the decision log + last-decision files are absent
   after a fenced-out cycle.

## Known limits

- Single POSIX host, single local filesystem. Cross-host / native-Windows
  fencing is out of scope here and is addressed by the host-locking artifact.
- Ownership fencing is not crash atomicity: a crash *between* the individual
  file writes inside the fenced closure can leave some written and others not.
  Each write is individually crash-atomic; multi-file idempotent recovery is
  deferred reliability work and is stated as such in code.
