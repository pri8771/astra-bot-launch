## One invocation, precisely

`bin/worker_once.py` is what a scheduler runs. Per firing:

1. consume lead direction from the canonical branch via plain `git`;
2. emit **exactly one** durable `SESSION_ONCE` heartbeat;
3. write a direction acknowledgement;
4. claim **at most one** task;
5. run that one bounded unit;
6. write an invocation receipt;
7. exit.

Direction is consumed **before** the heartbeat deliberately, so the heartbeat can
truthfully record which canonical SHA the session actually read — which is the
one thing a heartbeat is supposed to attest.

Exit codes: `0` unit completed · `3` no-overlap (benign) · `5` lead halted this
lane (benign) · `6` a live model route was configured but is not authorized
(refused) · `1` unexpected failure (a receipt records it) · `2` bad usage,
including an empty `--bots`. The systemd unit maps `3` and `5` to
`SuccessExitStatus`; the runbook explains how to read the raw code from Task
Scheduler and launchd, which have no equivalent.

## Refusing a live model route

An adversarial review of this session's code found that the entrypoint's
original claim to "never make a live model call" was false as written.
`reasoning.resolve_provider` picks a provider from `SBOTS_REASONING` alone, and
the V0.4 authorization gate only ever guarded
`divergence_prepare.execute_batch`. So `SBOTS_REASONING=claude-cli` on a
scheduled bounded worker would have spawned the real Claude Code CLI with no
manifest, no budget and no accounting.

Closed in two independent layers:

1. **Entrypoint.** `worker_once.py` consults `runtime/live_route_guard.py`
   before direction, before the heartbeat and before any provider exists. An
   unauthorized live mode exits `6` and writes an invocation receipt saying so.
2. **Spawn point.** `ClaudeCodeReasoningProvider` itself refuses unless a valid
   canonical manifest is in force, whenever it would launch the real CLI. This
   covers every entrypoint, including ones this session did not touch. An
   injected runner spawns nothing and is exempt, which keeps the existing
   `test_reasoning_cli` seam working unchanged.

This is also what makes the receipt honest. `live_model_call` was previously a
constant `False` that nothing ever set `True`; it is now derived from the
guard's decision, and `reasoning_route` records the mode and the reason beside
it. `audit()` separately counts refusals and receipts carrying no decision at
all, so "no live call" is a checked fact rather than an unset field.

Both layers are demonstrated in
`evidence/SB-V04-002-prepare/LIVE_ROUTE_REFUSED.txt`.

## The heartbeat, and why the old one could not be used

`bin/heartbeat_reporter.py` hard-requires an authenticated `gh`. On every host
this project has actually run on, `gh` is absent — which is exactly why LEAD-037
recorded 0 verified durable intervals while Issue #3 showed plenty of activity.
`bin/worker_heartbeat.py` implements the superseded timed cadence. Both are left
in place for the already-committed lane history.

`runtime/session_heartbeat.py` replaces them for new sessions:

- **`gh`-independent.** The durable write is an append-only JSONL ledger plus a
  latest-state JSON under `worker-reports/<lane>/`. No network, no subprocess,
  no token. A host with no GitHub transport still produces valid evidence.
- **One session, one heartbeat, structurally.** A second `emit` for the same
  `session_id` raises `DuplicateSessionHeartbeat`, checked across **all** lane
  ledgers rather than only the target lane — the guarantee is about the session,
  not the lane. A loop cannot manufacture liveness. Lane names are validated, so
  a lane cannot write outside the reports root.
- **No backfill.** `emit` re-stamps `started_at` from the real clock and
  re-stamps the contract fields (`schema_version`, `cadence_mode`,
  `session_status`), so a caller cannot hand in a forged timestamp or relabel a
  record's cadence. An earlier version only documented this; a review found the
  field was plainly settable and the test that "proved" otherwise asserted a
  `TypeError` on a kwarg no implementation has.
- **Ledger first, then the derived view.** A crash between the two leaves the
  durable history correct.
- **Issue visibility is best-effort, truthful and second.** The comment is
  attempted only AFTER the durable write succeeds, and its outcome is logged to
  `HEARTBEAT_ISSUE_POSTS.jsonl` beside the ledger rather than rewriting the
  append-only record. Posting first, as an earlier version did, meant a refused
  duplicate still announced a heartbeat that was never written. Every `gh`
  failure path returns `(False, reason)` and never raises.

Legacy schema-2 records already in a lane log are read and preserved untouched;
they simply carry no `session_id`, so they cannot block a new session.

This report's own session used this module: the first record it wrote is in
`worker-reports/windows-core/HEARTBEAT_LOG.jsonl`, session
`s-20260921T174817Z-0e532933`, and it accurately records
`issue_comment_posted: false, reason: "gh CLI not found on PATH"`. The Issue #3
visibility comment for this session was posted afterwards over this session's own
GitHub MCP transport; **the durable record was not rewritten to claim otherwise.**

## Claiming exactly one task, with no probe race

`claim_one` does not probe-then-acquire. It attempts each candidate's bounded
unit directly and treats `leasing.LeaseHeld` as "skip to the next candidate".
The first candidate that runs ends the loop. There is therefore no window in
which a task looks free but is taken before the real acquire, and at most one
unit ever executes per invocation. The existing lease/fence layer (SB-V03-004)
is reused unchanged; nothing about no-overlap or takeover semantics was
reimplemented.

## Crash and restart, proven with a real SIGKILL

`bin/prove_worker_once_crash.py` kills a genuine `worker_once.py` process
mid-invocation and inspects what it left behind. SIGKILL is used because it
cannot be caught, so no cleanup handler can tidy up — the worst case a scheduled
host actually faces. There is no test hook in production code: the kill delay is
calibrated against a real uninterrupted invocation and swept across the late part
of that window until one lands inside the bounded unit.

The committed run (`evidence/SB-V07-001/CRASH_RESTART_PROOF.json`) reached the
strongest stage, `mid_unit_lease_held` — killed with `cycle:social-a.lease.json`
still held — and all checks pass:

| check | result |
|---|---|
| killed invocation left an `incomplete` receipt | true |
| killed invocation claimed no success | true |
| killed invocation emitted its one heartbeat | true |
| next firing did not double-run while the dead lease was live (exit 3) | true |
| restart after lease expiry completed (exit 0) | true |
| restart wrote a new invocation id | true |
| no duplicate session heartbeats | true |
| audit reports the crash | true |

The middle one is the one a scheduled host most needs: a SIGKILL cannot release
a lease, so the dead process's lease file survives it. The lease TTL, not the
dying process, is what protects the next firing from running the same task twice.
The proof waits the TTL out rather than force-clearing the lease, because forcing
it would prove nothing about real recovery.

The kill point is timing-dependent. When a run does not reach
`mid_unit_lease_held`, the script reports the no-double-run check as **not
applicable** rather than as a pass, and names the stage it did reach.

## Invocation receipts and crash behaviour

`runtime/invocation.py` writes a receipt in two phases: `incomplete` before any
work, terminal on exit. A process killed mid-unit leaves a record that says
`status: "incomplete"` — not a missing record, and never a false success. A
restart writes a **new** invocation id rather than reusing the dead one.
`audit()` reports incomplete counts rather than hiding them, because an
incomplete record is precisely the durable signature of a crash that V0.7 needs
to be able to show.

The index carries an `open` row and a `close` row per invocation, so completed
invocations are counted by `close` rows and an unmatched `open` row is a visible
crash.

## Consuming lead direction without a human relay

`runtime/direction.py` uses `git fetch` + `git show <ref>:<path>` against the
canonical branch. No `gh`, no API token, no MCP, no owner copy/paste — the
clone's existing remote credentials are the whole transport, and nothing is ever
written to the remote.

Precedence: `social-bots/directions/<lane>.json` (a machine-readable contract the
lead can write) first, then `social-bots/STATE.json` `worker_lanes.<lane>` as the
fallback — so this works against canonical state **exactly as it exists today**,
with no migration needed before a first scheduled run. Lane keys in `STATE.json`
are logical (`core`) while report directories are host-flavoured
(`windows-core`), so an unmatched lane also matches on branch name.

A failed fetch degrades honestly: the last known ref is used and
`fetch_ok: false` plus the error is recorded. A lane with no canonical entry at
all raises rather than inventing direction — demonstrated in the evidence. A
lane the lead froze is read as `halt`, claims nothing, exits `5`, and still
leaves a heartbeat and a receipt, because "the session ran and was correctly told
to stand down" is itself the evidence.

`live_model_calls_authorized` defaults to `false` and stays false unless
canonical state explicitly grants it.

## Scheduler assets

`scheduling/` — Windows Task Scheduler v1.2 XML + idempotent
install/uninstall PowerShell; systemd template `.service` + `.timer` with a
user/system installer; launchd plist + installer. All use explicit
`__PLACEHOLDER__` tokens substituted by their installer, and
`tests/test_scheduling_assets.py` asserts no template carries a token its
installer does not substitute.

Single-instance policy everywhere: `MultipleInstancesPolicy=IgnoreNew`,
`Type=oneshot` + timer, `StartInterval` with no overlap. systemd adds
`NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome=read-only`
with scoped `ReadWritePaths`. Task Scheduler XML cannot carry environment
variables, so the Windows installer passes the runtime data root as `--home`
(`-SbotsHome`) rather than `SBOTS_HOME`; systemd and launchd set the env var
directly.

`README.md` and `RUNBOOK.md` both carry an explicit honesty boundary: installing
a scheduler entry is not evidence a worker ran.

## Known limitations — read these before accepting anything

1. **This is not SB-V07-002.** Nothing here is operational recurring-liveness
   proof. The demonstration is six direct CLI invocations on a Linux CCR
   container, not OS-scheduler firings on an owner-authorized always-on host.
   SB-V07-002 stays `BLOCKED` until such a host exists.
2. **No scheduler was actually registered anywhere.** The Windows, systemd and
   launchd assets are verified by parsing and by placeholder-coverage tests
   only — this environment has no Task Scheduler, no systemd and no launchd. No
   claim is made that they have been run on a real host.
3. **Windows and macOS runtime behaviour is unverified.** `leasing` reports
   `FLOCK_AVAILABLE` and falls back to `O_CREAT|O_EXCL` off POSIX; the strong
   locking path is proven on POSIX only. SB-V07-WIN-001 remains separate and
   unproven.
4. **The direction contract is partly prospective.** `directions/<lane>.json`
   does not exist yet in canonical state; today every read uses the `STATE.json`
   fallback. The precedence is tested, but the preferred path has never been
   exercised against a real lead-written file.
5. **Halt detection in the fallback is keyword-based** on the lane `activity`
   string. It correctly reads today's `frozen_authorization_consumed`, but it is
   a heuristic. A lead-written directions file with an explicit `halt` boolean is
   the reliable path.
6. **Direction consumption trusts the clone's remote.** A worker reading a
   compromised or wrong remote would consume wrong direction. The exact SHA is
   recorded so an audit can detect it after the fact; nothing prevents it up
   front.
7. **The demonstration ran with `--allow-deterministic`**, the diagnostic posture,
   because no adaptive provider is authorized. A production scheduled install
   must not set it; the runbook says so.
8. **Two heartbeat helpers remain in the tree** (`heartbeat_reporter.py`,
   `worker_heartbeat.py`). They are superseded for new sessions but were left
   untouched so already-committed lane history stays readable. The lead may want
   them retired explicitly.
9. **The crash proof is timing-dependent.** It reports the strongest stage it
   actually reached and marks the no-double-run check not applicable when it
   reached a weaker one. A committed `all_pass: true` at a weaker stage is a
   weaker claim, so read `strongest_stage_reached`, not just `all_pass`.
10. **The spawn-point guard covers the `claude-cli` route.**
    `SBOTS_REASONING=model` with a host-registered live callable is covered at
    the entrypoint but not at the spawn point, because the runtime cannot
    distinguish a live callable from the receipt-replay callable SB-V04-004
    legitimately registers.
11. **One-session-one-heartbeat is enforced across lanes within one reports
    root.** Two different roots (for example a worker misconfigured with a
    different `--report-root`) are not cross-checked.
12. **Invocation receipts now persist on each milestone**, so an `incomplete`
    receipt says how far a process got. That is several small extra writes per
    invocation; negligible here, but worth knowing for a host on slow storage.
