## Priority 1 — SB-V03-004 post-cycle success-receipt fencing (repaired)

LEAD-024 found that `worker.run_one_unit` wrote the `finish` (success-asserting)
receipt AFTER `decision.run_cycle`'s fenced commit returned, outside the fence —
so a worker that stalled after the cycle commit, lost its lease, and was taken
over could still emit a `finish` receipt implying `candidate_succeeded`/verified
success.

Repair (`runtime/worker.py`):
- the finish receipt now runs inside `fence.fenced_commit(...)`, i.e. its write is
  ownership-checked under the per-task lock; if the worker lost the fence after
  the cycle commit, `fenced_commit` raises `FenceLost` before the receipt is
  written, so no success receipt is emitted;
- the `FenceLost` handler now distinguishes pre-commit vs post-commit loss via a
  `cycle_committed` flag and records truthful evidence: a post-commit loss writes
  a `failure` receipt with `outcome="fence_lost_post_commit"`,
  `candidate_succeeded=false`, `cycle_committed=true`, explaining the cycle
  committed under valid ownership but ownership passed to the takeover worker
  before finalizing (success withheld, left to the takeover's reconcile);
- not fixed by increasing TTL; single-POSIX-host scope and the side-effect-free
  migration / fenced decision commit are preserved.

Regression: `tests/test_fencing.py::test_stale_owner_cannot_write_success_finish_receipt_after_takeover`
— cycle commit (1st fenced_commit) succeeds; a TTL-expiry + gen-2 takeover is
forced right before the finish-receipt write (2nd fenced_commit); the old worker
returns `outcome="fence_lost_post_commit"`, `committed=true`, writes NO `finish`
receipt on disk (only start + a truthful failure), and the takeover worker owns
the lease.

## Priority 2 — SB-V03-005 production persona read boundary (enforced)

LEAD-024 noted that wrapping raw readers in `_ADMIN_READERS` did not by itself
make raw whole-runtime APIs admin-only. Findings + repair:
- The actual production persona-facing reads were already persona-scoped: the
  dedup path (`pipeline.is_duplicate` → `pipeline.persona_content_keys`) and the
  analytics aggregate (`analytics.aggregate`, persona-filtered). Confirmed by
  production-path regressions.
- The one raw whole-runtime read on a production path was `worker._reconcile`'s
  `pipeline.publish_queue(bot)`. It is a DELIBERATE runtime-wide reconciliation
  read (a takeover must verify the whole external-effect surface), so it now goes
  through the explicit admin boundary `isolation.admin_all_records(bot,
  "publish_queue")` with a comment stating that intent — not a persona reader.
- `RuntimeState.content_history()` is annotated as an ADMIN/whole-runtime read
  with a pointer to the persona-scoped `isolation.persona_content_history`.
- Authoritative persona interface unchanged: `isolation.persona_records` /
  `PERSONA_SCOPED_READERS`; raw whole-runtime enumeration only via
  `isolation.admin_all_records`.

Regressions (`tests/test_production_read_paths.py`, 4 real-production-path tests):
dedup persona-scoped (one persona's history never makes another's a duplicate);
analytics aggregate never blends personas (10 vs 7, not 17); after real mixed
cycles every persona-scoped store read through the interface holds only that
persona's records; and `_reconcile` uses the admin boundary and sees all personas'
queue entries.
