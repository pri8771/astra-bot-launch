# Planning authoring contract

All task definitions below are proposals, not dispatched work or runtime implementation. Root owns shared/aggregate artifacts, commits and publication. Each lane writes only its assigned mission folders and `lanes/<lane>/` checkpoint/continuation. No agent writes Jira, contacts workers, alters source repositories, publishes accounts, installs packages, spends, or edits other lanes.

Each mission folder contains PLAN.md, TASKS.json, TASKS.md, EVIDENCE.md, evidence.json, requirements.json, UNRESOLVED_INPUTS.md, JIRA_RECONCILIATION.md, CHECKPOINT.md and CONTINUE.md. Keep checkpoint/continuation after evidence intake, plan/tasks, and review fixes. Source clones for read-only qualification may go under the workspace `work/` outside this checkout; never copy credentials or raw private runtime data into artifacts.

TASKS.json is an array. Every task has: id (OPO-01/WHB-01/CL-01/BF-01/GURU-01/LIPI-01 or SH-01), mission, title, goal, status (`planned` or `reuse_and_verify`), owner_role, source_repo, owned_paths (future exact proposed product paths, disjoint or dependency-serialized), evidence_refs (evidence IDs or source paths), dependencies (task IDs only), prerequisite_inputs (input IDs or explicit facts), implementation_steps (concrete array), deliverables, tests (specific pass/fail checks), review (identity requirement, exact-source hash and bounded repairs), acceptance (array of observable criteria), rollback, next_eligible_action, estimate {unit: `engineering_hours`, low, high, assumptions, dependency_risk}, jira {key:null, candidates:[], matching_action, writer}, effect_gates (gate/input identifiers), requirement_ids. Do not claim current Jira association from historical candidates; preserve estimates/actuals, request writer matching and native readback. Dependency IDs must resolve globally.

requirements.json is an array of {id, mission, requirement, task_ids, evidence_refs, acceptance}. Cover substantive distinct mission outcomes (e.g. OPO-O01) plus ALL A01-A18 separately per mission (id `OPO-A01`, etc.). Each row has a mission task, and may also reference shared tasks. Root creates shared/global rows. Every task must be relevant to at least one requirement. TASKS.md gives human-readable complete cards, not just titles.

evidence.json array fields: id, repository, ref, path, observed_at (actual ISO time), classification (array: implemented_tested/live_observed/historical/local_only/cloud_backed/missing), finding, proof_limits. Record actual inspected source revision, file names and observed checks. Do not equate source test files with executed tests. Prefer fresh source inspection to planning another inventory; targeted retained returns may be unavailable and must say so. No broad history ingestion.

Optional capability branches use `conditional_dependencies` entries with condition, dependencies and acceptance. `conditional_effect_gates` identifies the effect/capability condition and only the gates that apply to that enabled operation. Unknown/disabled branch stays blocked without preventing base/offline acceptance. Neither a pending input nor a failed verification satisfies positive capability acceptance. A valid evidence wait does not substitute for two completed real allowed cycles at final runtime acceptance. Resource conflicts serialize actual in-flight effects, not unrelated whole mission releases.

Shared requirement/task anchors (root owns definitions): A01 durable state + claims/fencing SH-02/SH-03; A02 deterministic event/due scheduling SH-04; A03 evidence decisions SH-05; A04 eligible actions and destination verification SH-06; A05 experiment evaluation/next decision SH-07; A06 owner nudges/revision acknowledgement SH-08; A07 questions/resume SH-08; A08 Jira/documentation outboxes SH-09; A09 bounded retry/review SH-10; A10 deduplication SH-06; A11 uncertain-effect reconciliation SH-06; A12 Windows process-tree cleanup SH-11; A13 restart/restore SH-11; A14 actionable alerts SH-12; A15 privacy/secret references SH-13; A16 model/tool/spend limits and zero idle inference SH-14; A17 exact-source independent review and real end-to-end cycles SH-15; A18 Windows independent execution and optional R730 migration SH-11/SH-16. SH-01 defines capability/admission/ownership contracts. Dependencies on shared tasks are for later autonomy integration, NOT a gate on separate workers' already-authorized useful releases.

Plans must explicitly integrate these mechanisms per mission, with actual events, actions, destination receipts, direction examples, restart faults, decisions and next experiments. Do not hide all integrations behind a vague runtime task. Define deferred effects separately from useful executable offline work. Proposed implementation paths are proposals, not existing verified assets. No new full Kai/Pri roadmaps, i9 work, Digital Temple, Retell, account leakage, unsolicited messages, or paid routes without exact authority.
